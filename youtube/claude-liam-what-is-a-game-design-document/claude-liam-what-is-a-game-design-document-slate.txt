Hedge this is Liam in Forbear. Two videos about game design documents landed in Bears' queue this week from two studios with very different games. They agree on one thing and disagree on nearly everything else, so I asked Claude to read both and to explain what a design document actually is using a document we can open. The one Zelda wrote for Bears' Claude platformer this morning. A game design document is the living outline of your game. It exists so that someone else can build it, and that someone is usually you a few weeks from now after the idea has changed. Everything else about the format follows from that one job. Act 1 the one reason. The first video puts it plainly, every design document exists to explain your game to someone else. That is the whole reason. If you are working alone, you might think that lets you off. It does not because the someone else is you three weeks in when the idea in your head has quietly changed, and the version you started building is the only record. This change and the document is where the change is written down instead of lost. Bear starter game had 20 optional cherries in its design. One day later the loop concept replaced them with ordered tasks. The record of no says why, two collectible systems serving one goal is bloat. Without that line, the cherries come back in a month as a new idea. So do you need one at all, the honest test from the first video. If the game is small enough to keep in your head, build it and keep it there. The moment you would forget a decision the project depends on, you need the document. The claw draft crossed that line on day one. It raised eight open questions before anyone wrote a line of code. The second video calls the same thing risk management. You anticipate the problems before core development when solving them is cheap. In the claw document, the riskiest mechanic malware that undoes a finished task has an acceptance test written before the mechanic exists. T22 task a done touch malware, expect dying a open ledger flips, a row today, a script later. That is a risk caught on paper. Back to what goes in. Both videos start in the same place, a high level description of what the player does and the design pillars, the handful of goals every later decision gets compared against. The first video says up to four or five and resists adding more. The mechanics and controls so you can tell what it plays like. Then only if it matters, look, sound, story and a rough timeline. Detail arrives when the game earns it. Here are Clawed's four, read the landing, earn another try, close the loop, small complete game. It's already existing code and two are new. Pillars earn their place the day two of them collide. Zelda had to rule that vague paths may hide which way but never where you land and that malware may undo one task but must name it. Without pillars, there is nothing to rule with. The second video's core loop question, what is the one thing the player does over and over? Answer it at three scales and you have most of the design. Clawed's micro loop exists, read a landing, commit, land or fail with a named cause. The miso loop is the proposal, task a, b, c, agate the flag. It is code, dashed as the document. A good document never lets you confuse the two. Mechanics and controls so it is possible to get an idea of what the game will be like to play. For Clawed that is ten lines, speed 160, jump velocity minus 320, six ticks of coyote time. The tests assert those numbers. The document points at the file instead of restating it which is the right move once code exists, the code is the truth and the document is the map. The second video's strongest argument is scope. The document defines what is in and what is out which is the only known cure for feature creep. Zelda tags every Clawed feature. It a 15 came out core 53% over her 40% line. She tried to reprioritize twice, could not get under without removing the loop and wrote bear two options instead of choosing. The document that argues is doing its job. In the sections you might skip, both videos list art direction, audio, story and a timeline. Clawed's document keeps all for honest, every visual is code drawn so no art files. The document is emergent from the ledger, no cutscenes. Characters are Clawed and only Clawed and the timeline is a blank with a question number on it because none exists. Writing the blank is better than pretending. Act 3 format matters. The first video proves format with a house. You know exactly how your house should look but you cannot build houses so you hire a builder and now you have to explain it. Imagine doing that in a word document. Even a perfect description is useless in that format. A blueprint holds the same information and the builder can use it. Read what goes in and decide how to present it. One way to do that is the OnePage method from StoneLibraryns 2010GDC talk. One page, one focus, a map chart, a drawing with the detail and callouts that all point back at it. One page is about as much as anyone will read including you and the page can grow as big as it needs to as long as everything on it still links to the focus. Otherwise you have several documents in one place. This is what a OnePage design looks like in Clawed's package. The session state machine, one focus, the five states the code already has. The callouts are the two proposals drawn dashed, a ledger tick inside playing and a gate that refuses to transition while a task is open. Everything on the page links to the machine, a reader who has never seen the code can argue with it. Format also depends on who it is for. A pitch to an investor explains the market and the audience and why it will sell. The document you make first is the one that helps you design and the second video adds where it lives, a shared document at first, then a wiki or a tool with version control once the team grows so you can see later why a decision was made. The key is one place everyone knows. Clawed keeps that history as a plain file. Version date author, sections added decisions logged, questions opened and closed and the why. The cherries went because two collectible systems served one goal. A change log without design reasoning is a timestamp. This one is eight lines and it already answers the question a new teammate asks first. Part four living then frozen. The standard definition calls it a living document. It changes as limits and new abilities are discovered. The second video adds the part people skip. Once production starts you freeze it. Not untouchable but the core mechanics, the story arc and the primary features stop moving because a core change late ripples into delays, cost and creep. After the freeze, changes are small and each one carries a written reason. Neither video had a tool for the hardest part telling what in the document is real. Zeldas draft tags every claim observed with a file in a line, inferred, assumption, missing. So the same page can hold the game that exists a tested first step slice and the game that is proposed tasks malware a fork without letting a reader mistake one for the other. That is the freeze made visible. One last thing a document can do that a meeting cannot, it keeps the argument. Zeldas notes at the end of the clawed draft or the pushback she would have spoken. The loop is a checklist until it has a verify step. The malware undo is the whole bet, gray box it first. The first fix is to answer two questions before anyone codes. Nobody was in the room, the document was. The verdict, a game design document exists to explain the game to someone else and that someone is usually you later. Start with the concept in four or five pillars, add mechanics and let detail arrive when the game earns it. Pick the format the reader can use, a page with one focus beats a novel nobody opens. Keep it living until production then freeze it and log every change with a reason and tag what is real. The two videos give you the first four. The clawed document shows the fifth.
